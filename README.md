# 拾益 / Card Benefits

一个只在浏览器本地保存数据的信用卡权益记录工具：自行添加卡片、年费与权益额度，记录使用日期和金额，查看当前周期余额及本年度使用统计。没有预置卡片、硬编码权益套餐或示例记录；具体权益规则请以发卡机构条款为准。

## 本地运行

技术栈：原生 TypeScript + Vite，无后端。需要 **Node.js 22.19+（22.x）** 和 npm。

```bash
npm ci
npm run dev
npm run check
npm test
npm run build
npm run preview
```

`npm run check` 执行 TypeScript 类型检查，不输出编译文件。`npm test` 使用 Node 自带测试运行器执行 `node --experimental-strip-types --test tests/*.test.ts`。生产文件输出到 `dist/`；Vite 的部署基础路径为 `/card-benefits/`，开发和预览时请访问终端给出的该路径。

## 金额、日期与统计口径

- **金额以整数分计算**，显示为人民币。没有汇率换算或多币种汇总：请始终使用同一计价单位，不要混录不同币种。
- 支持 **1900–2100 年**范围内的日期，按本地日历日期计算，不把日期当作 UTC 时间戳；“今天”取当前设备的本地日期。跨时区使用时，应自行核对记录日期。
- 权益周期从原始锚点按月、季度（3 个月）、半年（6 个月）或年（12 个月）递增。目标月份没有对应日时，夹取该月最后一天，但**保留原始锚点日**，不从夹取后的日期继续累加：月度 `1 月 31 日 → 2 月 28 日 → 3 月 31 日`（非闰年）；季度 `1 月 31 日 → 4 月 30 日 → 7 月 31 日`；半年 `8 月 31 日 → 次年 2 月 28 日 → 8 月 31 日`。以 `2 月 29 日` 为年度锚点时，非闰年夹取为 `2 月 28 日`，遇到闰年恢复 `2 月 29 日`。
- 当前周期**包含起始日、不包含下次重置日**，展示的结束日为重置日前一天；当前周期使用统计不计入未来日期记录。重置当天的使用属于新周期；锚点之前权益尚未生效，没有当前可用周期。
- 可以记录超过额度的使用；超额部分单独显示，可用余额最低为 0。未使用额度**不结转**到下一周期。
- 本年度统计区间为本地 **1 月 1 日至今天（均包含）**，包括此区间内仍保存着的历史周期使用记录，不包括未来日期记录。删除的记录不再参与统计。
- 年费对比以**当前仍保存的每张卡的 `annualFee` 各计一次后求和**，不按持卡时长或周期摊销。这不是实际年费扣款账本，也不会计算减免、返还或实际付款日期。
- 记录的权益金额与年费对比只是自报数据的参考，不保证等同于真实现金收益；不能据此推断银行承诺、达标状态或实际可兑换价值。

## 保存、备份与隐私

数据保存在当前浏览器的本地存储中。不同浏览器、设备和站点来源各自独立，**没有账号、认证、后端、同步或分析日志**；不连接银行，也不需要或收集银行卡号、CVV、登录凭据。请勿把这些敏感信息写入名称或备注。

- 清除站点存储、换浏览器或设备会使原记录不可见；隐私浏览模式关闭后也可能丢失数据。请自行定期导出备份。
- 导出得到设备上的个人 JSON 下载文件，不会自动上传。**不要将个人备份提交到 Git、上传到仓库或公开分享**。网站公开源代码不包含你的本地记录。
- 导入使用 **JSON `version: 1`** 格式，包含 `cards`、`benefits`、`usages`。导入前验证结构及数据约束；验证通过后仍须明确确认，才会**整体替换**当前数据，不是合并。
- 如需跨设备迁移，可自行通过可信方式传送导出的 JSON，再在目标设备导入；请先备份目标设备的数据，并注意导入会整体替换。
- 本地数据损坏时不会自动覆盖原数据；请保留原始内容或已有备份，再处理恢复。存储不可用或写入失败时会提示编辑未保存；看到失败提示后，不要把屏幕上的编辑当成可靠备份。
- 托管网站需要请求静态页面、脚本和样式等资源；托管平台仍可能处理这些访问请求。应用不向服务器发送卡片或使用记录。这里没有承诺离线可用，也没有 PWA 或自动跨设备同步／恢复能力。

## 使用边界与可访问性

本工具记录的是你输入的规则，不会自动获知银行调整、节假日规则、工作日延期、交易入账日或资格条件。日历周期与银行实际账期可能不同；请核对锚点、重置日和金额，并以银行信息为准。它不是财务建议或银行账单。

使用表单标签和文字状态辨认操作，不要仅依赖颜色；可用键盘逐项导航。原生日期输入的显示格式、日历弹窗与键盘操作受浏览器和系统影响，小屏或放大字体时可能需要滚动。未承诺所有浏览器／辅助技术组合均已测试；请在自己的设备上核对日期输入及保存反馈。

## 发布到 GitHub Pages（需仓库所有者手动操作）

仓库默认分支为 `main`。工作流不会修改仓库可见性或自动启用 Pages；请按以下顺序操作：

1. 在仓库 **Settings → General → Danger Zone → Change repository visibility** 中自行将仓库设为 **Public**。公开前确认仓库没有个人记录、备份或秘密。
2. 在 **Settings → Pages → Build and deployment → Source** 选择 **GitHub Actions**。
3. 将环境中已有的本次 PR 合并到 `main`；不需要另建 PR。也可以进入 **Actions → GitHub Pages → Run workflow**，选择 `main` 手动运行。
4. 等待安装、测试、构建与 `github-pages` 部署成功后，使用部署结果中的链接。

预期发布地址为 **https://yuchaozh.github.io/card-benefits/**；这是部署成功后的目标地址，**不表示网站当前已经上线**。

`.github/workflows/pages.yml` 使用官方 Pages Actions 和 Node.js 22：面向 `main` 的 PR 只执行 `npm ci`、`npm test`、`npm run build`，不配置 Pages、不上传发布产物、不部署。只有推送到 `main` 或在 `main` 手动触发才在构建后上传 `dist/`，随后由部署任务读取已启用的 Pages 配置并发布；不会自动启用 Pages。默认权限仅为 `contents: read`；Pages 配置读取与发布使用部署任务的 `pages: write` 权限，`id-token: write` 也仅限该任务。Vite 基础路径已明确设置，构建不依赖 Pages 配置输出；仅获取站点元数据的 Configure Pages 步骤无需 checkout。部署共享并发组且不取消正在运行的部署，PR 使用独立并发组。
